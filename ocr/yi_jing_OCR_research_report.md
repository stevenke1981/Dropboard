        ▼
  PNG 圖片 (每頁約 2-8 MB)
        │
        ▼
  Base64 編碼 → llama.cpp API

## 六、限制與挑戰

### 6.1 技術限制

1. **CPU 模式效能**: 未使用 GPU 加速，每頁平均處理時間 24-148 秒，全書需要 25+ 小時
2. **Base64 編碼傳輸**: 大型圖片（8MB PNG）導致 base64 約 11MB，無法透過 curl 命令列傳輸
3. **模型幻覺**: Unlimited-OCR 有時會脫離 OCR 模式，輸出英文幻覺文字而非中文辨識結果
4. **重複輸出**: 模型可能在特定條件下陷入重複循環（同一句子輸出數十次）

### 6.2 古籍特定挑戰

1. **直排文字**: 模型對中文傳統直排（由上至下、由右至左）文字的辨識效果不如橫排
2. **版式混亂**: 古籍頁面包含正文、注疏（雙行小字）、版心、魚尾等多種元素，模型難以正確區分
3. **異體字**: 宋代刻本的異體字與現代標準字形存在差異
4. **欄線干擾**: 版框、欄線等裝飾元素可能干擾文字區域檢測
5. **頁碼與標記**: 版心處的頁碼、刻工名等小字標記時常被誤識

### 6.3 資料限制

- 僅處理了前 100 頁（約 11.5%），全書仍需繼續處理
- 未進行人工校對，準確率為估計值
- 未與其他 OCR 引擎（如 Tesseract、PaddleOCR）進行對比測試
- PDF 為原色版掃描（869MB），黑白版（46.8MB）可能更適合 OCR

## 七、結論與建議

### 7.1 主要發現

1. **Unlimited-OCR 具備基礎古籍中文辨識能力**: 能夠辨識繁體中文、部分異體字以及古典注疏格式
2. **處理管線完整可用**: PyMuPDF → PNG → Base64 → llama.cpp API 的流程穩定可靠
3. **模型幻覺問題需關注**: 約 3% 的頁面出現幻覺，需後處理過濾

### 7.2 改進建議

1. **使用黑白版 PDF**: 建議改用 46.8MB 黑白版掃描，可減少 PNG 檔案大小，加速傳輸
2. **優化 Prompt**: 嘗試自訂 prompt 如「逐字識別此古籍頁面中的所有中文文字」可能提升準確率
3. **批次後處理**: 開發專用後處理腳本清理重複文字與幻覺
4. **GPU 加速**: 如可用 GPU，可大幅縮短處理時間
5. **雙引擎驗證**: 比對 Unlimited-OCR 與 PaddleOCR/Tesseract 的結果，取高可信度部分
